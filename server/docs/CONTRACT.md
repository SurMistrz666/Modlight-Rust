# Modlight web panel: the contract between the SPA and the Rust server

The web panel is a client-side app (`server/web`, Vite + React 19) that keeps
every upstream React component and translation, and gets from the Rust server
what upstream's Next.js server layer used to produce: the HTML document, the
data of each page, and the results of the server actions. This document is the
work order for that server side. It complements `PORT.md` (sections 7, 8, 11)
and, where the two differ in detail, this document is the more precise one.

Upstream (`upstream/Modlight`) stays the specification of behaviour. Every
statement below names the upstream code it comes from.

## 1. The SPA

### 1.1 Layout of `server/web`

| Path | What it is |
|---|---|
| `components/`, `hooks/`, `types/`, `lib/` (part), `app/globals.css`, `app/error.tsx`, `app/(app)/dashboard/error.tsx`, `app/s/[code]/unlock/unlock-form.tsx`, `messages/{en,pl}/*.json` | Byte-for-byte copies of upstream files, written by `scripts/sync-upstream.mjs`. `upstream.lock.json` holds the sha256 of each; `npm run sync:check` proves they are still verbatim. `@/x` resolves here, exactly as upstream's `@/*` path alias does. |
| `src/overrides/` | Browser versions of upstream modules that cannot run in a browser, at the same `@/` path (they win over the copies): client ports of the upstream Server Components under `components/` (13 files), type mirrors of server-only `lib/` modules (generated by `scripts/gen-type-mirrors.mjs`), and `lib/config.ts` (the public part of upstream `config`). |
| `src/rpc/actions/<module>.ts` | One generated RPC stub per upstream `app/actions/<module>.ts` (`scripts/gen-actions.mjs`): same exports, same parameter and return types, exported types copied. `@/app/actions/*` resolves here. |
| `src/shims/` | `next/link`, `next/navigation`, `next/dynamic`, `next-intl` (on `use-intl` 4.13.0, the version next-intl 4.13.0 uses) and `client-only`. Any other `next/*`, `next-intl/*` or `server-only` import fails the build. |
| `src/pages/` | Ports of upstream `app/**/page.tsx` and `layout.tsx` (Server Components) as client components, mirroring the `app/` tree. Each exports a `...Props` type: the page data the server sends (section 6). |
| `src/routes/` | The react-router data router: route tree, the loader, error/loading boundaries, code splitting. |
| `src/runtime/` | Tagged JSON, the `/_page` and `/_rpc` clients, navigation, Next-compatible redirect/not-found errors. |
| `src/contract/` | TypeScript types of the layout data, route ids, and the drizzle row shapes that cross the wire. |
| `fixtures/` | Example payloads for every page (`fixtures/pages/*.json`), shared layout data (`fixtures/layouts.json`) and canned action answers (`fixtures/actions.json`). They double as worked examples of section 6. |
| `tests/` | vitest + jsdom: the smoke test mounts every fixture page; `runtime.test.tsx` pins the wire formats. |
| `scripts/` | `sync-upstream.mjs`, `gen-actions.mjs`, `gen-type-mirrors.mjs`, `audit-bundle.mjs`, `size-report.mjs`. |

Every file in `src/` that ports or mirrors upstream code names it with an
`@upstream <path>` tag; `upstream.lock.json` records the upstream hash each port
was written against, so `npm run sync:check` fails when upstream moves under a
port.

### 1.2 Build and run

Node is a build-time tool only. Use pnpm 10.33.0 (as upstream):

```sh
cd server/web
npx -y pnpm@10.33.0 install          # versions pinned by pnpm-lock.yaml (seeded from upstream's)
npm run build                        # tsc --noEmit, then vite build -> dist/
npm test                             # vitest: 42 smoke + 9 runtime tests
npm run audit:bundle                 # after a build: no server code in dist/
npm run size                         # first-load sizes against the reference on :8420
npm run sync:check                   # copies verbatim, ports current
npm run dev                          # vite on 127.0.0.1:5173, proxying to the Rust dev server :8421
npm run dev:fixtures                 # vite on 127.0.0.1:5173, no backend: fixtures/pages/*.json
```

`dist/` is what the Rust server serves: `dist/index.html` (the document
template, section 2), `dist/assets/*` (hashed JS, CSS, fonts; immutable) and
`dist/.vite/manifest.json` (entry and chunk names, if the server wants to emit
preload hints).

Dev server: every request that is not the SPA's own module or a page document
(`/_rpc`, `/_page`, `/api/*`, `/upload`, `/oembed`, media paths such as
`/{tag}/{code}/raw`, `/s/{code}`, `/avatar/*`, `/bg/*`, `/embed/*`,
`/download/app`, `/icon.svg`...) is proxied to `MODLIGHT_RUST_URL`
(default `http://127.0.0.1:8421`). Page documents get the bare `index.html`; the
SPA then fetches `/_page` for the first page too.

Fixture mode: `npm run dev:fixtures`, then open any page URL. The fixture is
chosen by the route the URL matches, or explicitly with
`?__fixture=<file name>` (e.g. `/x?__fixture=not-found`,
`/alicja/a.png?__fixture=media-gate`). Server actions answer from
`fixtures/actions.json` (`"<module>.<export>": <envelope>`) or with an error
envelope.

## 2. Serving the SPA: the HTML document

### 2.1 Which requests get the document

Every `GET`/`HEAD` for a **page URL** (section 6; the route table is
`src/contract/routes.ts`) answers with `dist/index.html`, filled in as below,
after the same request processing upstream applies to a page:

1. `proxy.ts`:
   - On the shortener host (`SHORTLINK_URL`'s hostname), a path other than `/`
     that is not in `PASSTHROUGH` is rewritten to `/s<path>` before routing.
     **The SPA's own paths must be added to that passthrough list** (upstream
     has `_next` there): `/_page`, `/_rpc`, `/assets/`. A rewritten page URL is
     resolved as the rewritten path, but the document is served at the URL the
     browser asked for (the SPA renders whatever route `/_page` reports).
   - `/dashboard*` without a Better Auth session cookie: `307` to
     `/login?next=<pathname>` (pathname only, no query).
2. The page's own logic (section 6): `307` redirects (`Location` header, no
   body needed), `404` (not-found document), or the page.

Unknown paths that are neither a page nor a route handler get the not-found
document with status `404` (PORT.md section 6).

Status codes: `200` page, `404` not found, `307` redirect (Next's `redirect()`;
`308` only for `permanentRedirect()`, which upstream pages never call), `500`
when computing the page failed (the error document, section 4.4).

Headers on documents: the `next.config.ts` rules for the path (security
headers, `appCsp`; `/authorize` gets `authorizeCsp` instead), plus
`Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` and
`Content-Type: text/html; charset=utf-8`, as the reference sends. No
`X-Powered-By`. `dist/assets/*` are content-hashed: serve them with
`Cache-Control: public, max-age=31536000, immutable`.

The production CSP works unchanged for the SPA: its scripts and styles are
same-origin files, the only inline script is the theme script below
(`'unsafe-inline'` is already in `script-src`), the page payload is
`type="application/json"` (never executed), and the bundle uses no `eval`
(checked by `scripts/audit-bundle.mjs`).

### 2.2 Filling in `dist/index.html`

The template has three markers. Replace each **exactly once**:

```html
<html data-ml-html class="geist-sans geist-mono h-full antialiased">
...
    <!--ml-head-->
...
    <!--ml-body-->
```

**`data-ml-html`** (the attribute inside the `<html>` start tag) becomes the
attributes upstream's root layout renders on `<html>`, HTML-escaped:

```
lang="{locale}" data-mode="{mode}" data-theme="{skin}"
```

plus, when the page has a wallpaper, ` style="--ml-bg-image:url(&quot;{url}&quot;);--ml-bg-dim:{dim}" data-bg="on"`.

- `locale`, `mode`: from the root layout data (section 5.1).
- `skin` and the wallpaper: upstream paints `data-theme` from the root layout
  and then, on pages that render `<ThemeApplier>`, an inline script switches it
  (and the wallpaper) before the first paint. The SPA has no server-rendered
  body, so the document must carry the **final** values directly:
  - pages under `(app)`: `resolveTheme(layouts["(app)"].theme)` and
    `layouts["(app)"].background`;
  - `/{tag}/{code}` and `/{code}` (all three views): `resolveTheme(props.ownerTheme)`
    and `props.ownerBackground`;
  - `/a/{tag}/{slug}`: `resolveTheme(props.owner.theme)` and `props.background`;
  - `/u/{tag}`: `resolveTheme(props.owner.theme)` and `props.background`;
  - `/s/{code}/unlock`, `/s/{tag}/{name}/unlock`: `resolveTheme(props.ownerTheme)` and `props.background`;
  - every other page (and not-found / error documents): `layouts.root.skin`, no wallpaper.

  `resolveTheme` is `lib/themes.ts` (aliases `modern` -> `default` etc.; unknown
  -> `DEFAULT_THEME`). `dim` is the number from `BackgroundStyle.dim`
  (`clampDim(...)/100`, e.g. `0.7`), written with JavaScript's `String(number)`.
- The class list is fixed: `geist-sans geist-mono` are the stable names of the
  two `next/font` variable classes (`src/fonts/geist.css`), then
  `h-full antialiased` from upstream.

**`<!--ml-head-->`** becomes the page's head: `<title>{meta.title}</title>`
followed by one element per `meta.tags` entry, in order, each with the extra
attribute `data-ml-head=""` (the SPA replaces exactly those elements on later
navigations):

```html
<title>Sign in - Modlight</title><meta name="description" content="..." data-ml-head=""/><meta name="application-name" content="Modlight" data-ml-head=""/>
```

Text and attribute values HTML-escaped (`&`, `<`, `>`, `"`). Section 6 gives
`meta` for every page; the `<link rel="icon">` / `apple-touch-icon` tags upstream
derives from `app/icon.svg` and `app/apple-icon.png` are already in the template.

**`<!--ml-body-->`** becomes two scripts, in this order:

1. next-themes' blocking script (exactly what `next-themes@0.4.6` emits for the
   root layout's `<ThemeProvider attribute="data-mode" defaultTheme={mode}
   enableSystem disableTransitionOnChange>`), with `"system"` replaced by the
   JSON string of `layouts.root.mode`:

   ```html
   <script>((a,b,c,d,e,f,g,h)=>{let i=document.documentElement,j=["light","dark"];function k(b){var c;(Array.isArray(a)?a:[a]).forEach(a=>{let c="class"===a,d=c&&f?e.map(a=>f[a]||a):e;c?(i.classList.remove(...d),i.classList.add(f&&f[b]?f[b]:b)):i.setAttribute(a,b)}),c=b,h&&j.includes(c)&&(i.style.colorScheme=c)}if(d)k(d);else try{let a=localStorage.getItem(b)||c,d=g&&"system"===a?window.matchMedia("(prefers-color-scheme: dark)").matches?"dark":"light":a;k(d)}catch(a){}})("data-mode","theme","system",null,["light","dark"],null,true,true)</script>
   ```

2. The page payload (section 4), exactly the JSON `GET /_page` would return for
   this URL, with every `<` written as `<` (so no `</script>` can end it):

   ```html
   <script id="__MODLIGHT_PAGE__" type="application/json">{"route":"/(auth)/login",...}</script>
   ```

The SPA reads the payload once, loads the translations and the page's code, and
renders without asking `/_page` again. A document without the payload (or with
the markers unreplaced) still works: the SPA fetches `/_page` itself and fills
in `<html>` (that is what the vite dev server does).

Optional, for speed only: `Link` preload headers for the fonts and the entry CSS
(the reference sends them for its own files), and `<link rel="modulepreload">`
for the page's chunk and the locale's messages chunk, read from
`dist/.vite/manifest.json` (`src/pages/.../page.tsx`, `src/messages/<locale>.ts`).

## 3. Tagged JSON

Every JSON body in both directions (page payloads, RPC arguments, RPC results)
is plain JSON plus four tags for values JSON cannot carry (PORT.md section 7):

| Value | Wire form |
|---|---|
| `Date` | `{"$date": "2026-10-18T12:00:00.000Z"}` (ISO 8601 with milliseconds, `Z`) |
| `undefined` | `{"$undefined": 1}` |
| `bigint` | `{"$bigint": "123"}` |
| `NaN`, `Infinity`, `-Infinity` | `{"$num": "NaN"}`, `{"$num": "Infinity"}`, `{"$num": "-Infinity"}` |

An object with exactly one key that is one of these tags is decoded as the
value; anything else is plain JSON. `undefined` survives inside objects and
arrays in both directions: the browser sends `{"locale": {"$undefined": 1}}`
for `updatePreferences({ locale: undefined })`, because upstream code tests
`"locale" in input` and React's server-action encoding keeps the key. In
results, a field that is absent and a field that is `undefined` are the same to
the SPA, so the server may simply omit `undefined` fields.

Where upstream passes a `Date` across (a Server Component prop of type `Date`,
or an action that returns drizzle rows), send `{"$date": ...}`; where upstream
converts to a string first (`createdAt.toISOString()`), send the string. The
types in section 6 and in `src/rpc/actions/*.ts` say which.

Implementation: `src/runtime/tagged-json.ts`; tests: `tests/runtime.test.tsx`.

## 4. Page data: `GET /_page`

### 4.1 Request

```
GET /_page?path=<pathname>&<the page's own query parameters, in order>
Accept: application/json
X-Modlight-Page: 1
Cookie: ...
```

The **first** `path` parameter is the page's pathname (URL-encoded); every
other parameter, in order and including a second `path`, is the page's own
query string. `/dashboard?folder=a&page=2` is asked as
`/_page?path=%2Fdashboard&folder=a&page=2`.

The server evaluates the request exactly as it would a document request for
that URL (section 2.1, including the shortener rewrite and the `/dashboard`
cookie gate), with the request's own cookies and headers (`Accept-Language`,
`User-Agent` and `Host` matter to some pages).

### 4.2 Responses

Always JSON (tagged), `Content-Type: application/json`,
`Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate`.

| Case | Status | Body |
|---|---|---|
| a page | 200 | `{"route", "params", "layouts", "props", "meta"}` |
| upstream `redirect(url)` (or the proxy gate) | 200 | `{"redirect": "<url>", "status": 307}` |
| upstream `notFound()`, or no page at this path | 404 | `{"notFound": true, "layouts": {"root": ...}, "meta": {...}}` |
| not a page: a route handler or a file (`/s/{code}`, `/{tag}/{code}/raw`, `/download/app`, `/oembed`...) | 200 | `{"document": true}` |
| computing the page failed | 500 | `{"error": {"message", "digest"}, "layouts": {...whatever loaded}, "route"?, "params"?}` |

- `route`: the page id (`src/contract/routes.ts`), i.e. the upstream path under
  `app/` without `/page.tsx`: `"/(app)/dashboard/folders"`,
  `"/[userCode]/[mediaCode]"`, `"/s/[code]/unlock"`. When the server resolves a
  URL to a different page than its shape suggests (the shortener rewrite), the
  SPA renders the page `route` names.
- `params`: the route's dynamic segments, decoded (`{"userCode": "alicja",
  "mediaCode": "a.png"}`).
- `layouts`: the data of every layout on the route's path: always `root`, plus
  `"(app)"` or `"(auth)"` (section 5).
- `props`: the page's data (section 6).
- `meta`: `{"title": string, "tags": [{"tag": "meta" | "link", "attrs": {...}}]}`,
  the resolved upstream metadata of this page as head elements (section 6 per
  page; section 2.2 for how a document renders it). The SPA sets
  `document.title` and swaps the tags on every navigation, as Next does.
- `redirect`: the target exactly as upstream builds it (a path, or an absolute
  URL for the direct-media bot redirect). The SPA follows a same-origin page
  path with a client navigation and anything else with a full load.
- `notFound`: `layouts.root` is required (locale and skin of the not-found
  page); `meta` is what upstream renders for a 404 (section 6.0).
- `document`: tells the SPA to load the URL as a document.
- `error`: see 4.4.

### 4.3 When the SPA asks

- First page of a visit: never (the payload is inlined, section 2.2).
- Every client navigation (links, `router.push/replace`, back/forward): one
  request for the new URL. Unlike Next, the layouts are part of every answer;
  the SPA always uses the latest (so the sidebar counts are fresh after a
  navigation, where Next would keep the old layout until a refresh).
- `router.refresh()`, and after every action whose envelope says `revalidate`:
  one request for the current URL.

### 4.4 Errors

When upstream would throw while rendering (a database outage, a bug), answer
`500` with `{"error": {"message": "<message>", "digest": "<digest>"}}`. In
production the message must be React's masked text, the same for every error:

```
An error occurred in the Server Components render. The specific message is omitted in production builds to avoid leaking sensitive details. A digest property is included on this error instance which may provide additional details about the nature of the error.
```

`digest` is any opaque string that lets an operator find the logged error (Next
uses a numeric hash); the error pages show it as "Reference: <digest>".

Where the failure happened decides which error page shows, as with Next's
`error.tsx` boundaries:

- a page under `/dashboard`: include `layouts.root` and `layouts["(app)"]` and
  `route`/`params`: the panel stays and `app/(app)/dashboard/error.tsx` replaces
  the content;
- anywhere else, or when a layout's own data failed: `layouts.root` only (or
  nothing): `app/error.tsx` replaces the page.

Their "Try again" button fetches the page again.

## 8. Better Auth endpoints the browser calls

`lib/auth-client.ts` (copied verbatim) is `createAuthClient({ plugins:
[adminClient(), twoFactorClient(), inferAdditionalFields<typeof auth>()] })`
from better-auth 1.6.13, with no `baseURL`: it calls `<page origin>/api/auth/*`
with `credentials: "include"` (same origin). The wire format of each endpoint
is Better Auth's own (PORT.md section 9): JSON bodies, JSON answers, errors as
`{ "code", "message" }` with an HTTP 4xx/5xx status, session cookies via
`Set-Cookie`. The components read `error.message`, `error.status` and the data
fields named below, so those must match Better Auth exactly.

| Browser call (component) | Request | Body | What the component reads |
|---|---|---|---|
| `signOut()` (components/app-shell.tsx, account menu) | `POST /api/auth/sign-out` | `{}` | nothing; then `router.push("/login")`, `router.refresh()` |
| `authClient.twoFactor.verifyTotp` (components/auth/two-factor-form.tsx, sign-in step 2) | `POST /api/auth/two-factor/verify-totp` | `{ "code": "123456", "trustDevice": boolean }` | `error`; on success `router.push(next)` + `refresh()` |
| `authClient.twoFactor.verifyBackupCode` (same form, backup code mode) | `POST /api/auth/two-factor/verify-backup-code` | `{ "code": "..." }` | `error` |
| `authClient.twoFactor.verifyTotp` (components/profile/SecuritySection.tsx, confirming setup) | `POST /api/auth/two-factor/verify-totp` | `{ "code": "123456" }` | `error.message` |
| `authClient.twoFactor.enable` (SecuritySection) | `POST /api/auth/two-factor/enable` | `{ "password": "..." }` | `data.totpURI`, `data.backupCodes`, `error.message` |
| `authClient.twoFactor.disable` (SecuritySection) | `POST /api/auth/two-factor/disable` | `{ "password": "..." }` | `error.message`; then `router.refresh()` |
| `authClient.changePassword` (SecuritySection) | `POST /api/auth/change-password` | `{ "currentPassword", "newPassword", "revokeOtherSessions": true }` | `error.message` |
| `authClient.requestPasswordReset` (components/auth/forgot-form.tsx) | `POST /api/auth/request-password-reset` | `{ "email", "redirectTo": "/reset" }` | `error.status === 400` only (anything else shows the neutral confirmation) |
| `authClient.resetPassword` (components/auth/reset-form.tsx) | `POST /api/auth/reset-password` | `{ "newPassword", "token" }` | `error` |
| `signUp.email` (components/auth/register-form.tsx) | `POST /api/auth/sign-up/email` | `{ "name", "email", "password" }` plus `"registrationKey"` when the page says a key is required | `data.token` (truthy = signed in), `error` (`code`/`message`, see the `hooks.before` gate in upstream lib/auth.ts: `SIGNUP_RATE_LIMITED` 429, `REGISTRATION_DISABLED` 403, `REGISTRATION_KEY_REQUIRED` / `REGISTRATION_KEY_INVALID` 400) |
| `authClient.getSession` (register-form, only when sign-up returned no token) | `GET /api/auth/get-session` | none | `data.session` |

`components/auth/auth-error.ts` turns an error into text: `error.message` when
present, else a translated fallback, so Better Auth's English messages show
as they do upstream.

Links the browser *follows* (documents, not fetches), which the Rust server
must answer like Better Auth does:

- the e-mail verification link (`GET /api/auth/verify-email?token=...&callbackURL=...`),
- the password-reset link (`GET /api/auth/reset-password/<token>?callbackURL=/reset`),
  which redirects to `/reset?token=<token>`, or to `/reset?error=INVALID_TOKEN`
  for a bad or expired token (the `/reset` page shows the "expired" card for any
  `error` parameter or a missing `token`).

Sign-in itself is not a client call: the login form uses the
`login-identifier.signInWithIdentifier` server action (section 7), and the
admin, invite and verification flows call Better Auth server-side from actions.

## 10. What the SPA does on its own

What the server can rely on, and what it does not need to do:

- **Navigation.** `<Link>` and `useRouter().push/replace` navigate client-side
  when the target is a page of the SPA on the same origin (`src/routes/tree.tsx`
  lists the pages, and the route-handler paths so that matching follows Next's
  precedence: `/s/promo` is the short-link handler, not a `[userCode]/[mediaCode]`
  page). Modified clicks, `target`, `download`, other origins and non-page paths
  are left to the browser. `scroll: false` keeps the scroll position, otherwise a
  navigation scrolls to the top; back/forward restore it.
- **`router.refresh()`** fetches `/_page` for the current URL and re-renders with
  the new data, keeping component state (Next's semantics).
- **Loading UI.** `app/(app)/dashboard/loading.tsx` replaces the content while a
  navigation moves to a *different child segment* of `/dashboard`
  (`/dashboard` -> `/dashboard/folders`), not for query-only changes or deeper
  changes under the same child: that is when Next 16 creates a new Suspense
  boundary (its segment state keys ignore search params). Elsewhere the old page
  stays until the new one is ready.
- **Error UI.** `app/(app)/dashboard/error.tsx` for errors under `/dashboard`
  (the panel shell stays), `app/error.tsx` otherwise, `app/not-found.tsx` for
  `notFound`. Both error pages' "Try again" refetches the page. Server errors
  arrive as described in 4.4.
- **Redirect errors.** An action redirect navigates (push) and rejects the
  action's promise with Next's `NEXT_REDIRECT` error; a `redirect()` that escapes
  to the window is turned into a navigation, as Next's app router does.
- **Head and `<html>`.** On every navigation the SPA sets `document.title` and
  replaces the `data-ml-head` elements from `meta`. When the root layout data
  changes (after a language or skin change and a refresh) it updates `lang`,
  `data-mode` and `data-theme` on `<html>`, as React does when the root layout's
  rendered attributes change; on public pages `<ThemeApplier>` switches the skin
  and wallpaper after each navigation and writes `ml_skin` on `/dashboard*`.
- **Translations.** Bundled: `messages/{en,pl}/<namespace>.json` for the 17
  namespaces `i18n/request.ts` loads, one chunk per locale. The server only
  says which locale (`layouts.root.locale`) and time zone (`layouts.root.timeZone`).
- **Cookies the browser writes that the server reads**: `ml_mode`
  (components/theme-toggle.tsx), `ml_skin` (components/theme-applier.tsx, panel
  only), `ml_sidebar` (components/app-shell.tsx), `ml_dupes_snooze`
  (components/duplicates/DuplicateReminder.tsx). `ml_locale` is written only by
  the `account.updatePreferences` action.

## 11. Deviations from upstream

Components and translations are byte-for-byte upstream (`upstream.lock.json`,
`npm run sync:check`). What had to change, and why:

**Ported Server Components** (`src/overrides/components/`, each starts with a
header naming the change):

| File | Change | Why |
|---|---|---|
| `landing/{cta,features,hero,large-files,sharex,site-footer,site-nav}.tsx`, `dashboard/EmptyState.tsx` | `async` dropped; `getTranslations` (next-intl/server) -> `useTranslations` | async components cannot render in a browser |

| `viewer/MediaViewer.tsx` | `getTranslations`/`getFormatter`/`getLocale` -> hooks; `config` and `sandboxShape` resolve to browser versions | `lib/config` and `lib/media/render-ticket` are server modules; the browser config holds the public fields, the render-ticket mirror holds the pure `sandboxShape` |
| `duplicates/DuplicateReminderSlot.tsx` | renders the decision passed as `state` | the snooze check and the count are server work (`layouts["(app)"].duplicateReminder`) |

**Ported pages and layouts** (`src/pages/`): the JSX after `return` is upstream's,
except where a value upstream computed from server-only inputs is now a prop:
`(app)/layout.tsx` (all shell props), `admin/page.tsx` (`<ServerDisk insights>`),
`profile/page.tsx` (`folders`, `avatarUrl`, `backgroundUrl`), `links/page.tsx`
(`userCode`, `canUseRoot`), `tokens/page.tsx` (`<AppCard release>`, `user`),
`duplicates/page.tsx` (`userCode`), the public pages' `background`, and
`(auth)/authorize/page.tsx` (`session`; the signed-out redirect happens on the
server). `app/layout.tsx`'s `<html>`/`<body>` are the document template
(section 2.2). Pages whose query handling is presentation only read it in the
browser: `/2fa` and `/login` (`next`, through upstream's `safeNext`) and
`/reset` (`token`, `error`).

**Infrastructure**:

- Fonts: the same Geist woff2 files and `@font-face` rules as upstream's
  `next/font` output, served from `/assets/` with the stable class names
  `geist-sans` / `geist-mono` (Next's are hashed).
- Translations are bundled in the SPA instead of travelling in the page data
  (PORT.md section 8 lists `messages` under the root layout; section 11 says the
  SPA bundles them; this contract chooses bundling, see 12.1).
- Layout data arrives with every navigation and the SPA uses the newest (Next
  keeps a shared layout until a refresh): the sidebar counts can be fresher.
- A server action's promise settles after the page data it revalidated has
  been fetched again (one extra round trip; Next ships both in one response).
- `next/dynamic({ ssr: false })` is `React.lazy` + `Suspense` with the same
  `loading` fallback; `useRouter().prefetch` is a no-op.
- `<ThemeApplier>`'s inline script does not run in a client render (it never
  runs on client navigations upstream either); the server-rendered document
  carries the final skin instead (section 2.2), and its effect does the rest.
- `server-only` and Node globals: `Buffer` and `process.env` are declared for
  the type checker only (`src/node-globals.d.ts`), because two shared upstream
  modules name them in server-only code paths; `NEXT_PUBLIC_*` are inlined at
  build time as Next does.

## 12. Open questions for the backend

1. **Translations in the payload or in the bundle.** PORT.md section 8 lists
   `messages` in the root layout data; this contract bundles them in the SPA
   (one chunk per locale, cached) and sends only `locale` and `timeZone`. If the
   server would rather send them (for example to serve a translation fix without
   a rebuild), the SPA change is small: say so before implementing either way.
2. **Shortener host and the SPA's paths.** `proxy.ts` rewrites every path on the
   shortener host except its `PASSTHROUGH` list (`_next`, `api`, `s/`, ...). The
   SPA needs `/_page`, `/_rpc` and `/assets/` in that list (section 2.1); the
   unlock page is the one SPA page reached on that host (`/promo/unlock` is
   rewritten to `/s/promo/unlock`, and `/_page` must report that route).
3. **Upstream returns secrets to their owner through two actions.**
   `shortlinks.listShortLinks()` and `tokens.myTokens()` return whole rows
   (`passwordHash`, `tokenHash`); the pages strip them, but the actions are
   callable endpoints. 1:1 keeps that; dropping the two columns from the RPC
   answers would break nothing in the SPA (no component reads them).
4. **Masked error messages.** Several components show `err.message` from a
   failed action (FolderTree, FolderBrowser, FileMenu, PasteEditor, SettingsForm,
   UserManager, OrphanFiles, Maintenance). Upstream in production shows React's
   masked text there (section 4.4); 1:1 means sending that text in `error.message`.
   A development mode that sends the real message (as `next dev` does) is fine.
5. **Upstream UI bug kept as is.** components/tokens/OneClickShareX.tsx passes a
   function for the plain argument `{fileName}` of `tokens.oneClick.downloadsHint`,
   so the file name never renders (React drops a function child; dev builds log
   an error). Fixing it means changing a component or the message.
6. **`/authorize` after an in-app sign-in.** `/authorize`'s wider CSP (loopback
   `connect-src`) only applies to a document loaded at `/authorize`. After the
   sign-in redirect the login form navigates there client-side (upstream does the
   same with Next's router), so the document is still `/login`'s and the loopback
   POST is blocked; the prompt then offers the manual copy. 1:1 keeps it; a
   document navigation for `/authorize` would fix it.
7. **Side effects of `GET /_page`.** As with upstream page loads, some page data
   has effects: the media page counts a view (and can burn a one-time link), the
   admin file browser writes an audit entry. Prefetching is off in the SPA, so
   only a real navigation triggers them.
8. **Dev server port.** `npm run dev` uses `127.0.0.1:5173` (PORT.md section 3
   has no row for it).
